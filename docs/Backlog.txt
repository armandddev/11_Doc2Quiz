# Backlog & Planning de sprints — Générateur de QCM pédagogique (Ollama / gemma)

## 0. Contexte du projet

- **Objectif** : transformer des supports de cours (PDF, Markdown) en QCM d'auto-évaluation, avec distracteurs plausibles, feedback pédagogique, contrôle qualité, export LMS (Moodle XML / GIFT).
- **Contraintes techniques** : 100% local (souveraineté des données), Ollama comme unique moteur LLM, modèle standardisé `gemma4:12b`, communication via API REST.
- **Contraintes fonctionnelles fortes** (à ne jamais perdre de vue, elles traversent tous les sprints) :
  1. Ne jamais paraphraser/copier des phrases du cours → générer des questions d'application (ex : exercices en maths à partir du cours, pas des questions "recopiées").
  2. Non-répétition : un même support ne doit jamais reproduire le même QCM à deux générations différentes.
  3. Profils utilisateurs persistants (Docker + volume/DB) avec historique de générations.
  4. Apprentissage des préférences implicites (ex : "5 questions" demandé une fois → réutilisé par défaut ensuite) et explicites (feedback négatif du type "supprime tout, c'est mal fait").
  5. L'IA doit être **critique** vis-à-vis de l'input (ex : signaler "support trop court/pas assez de contenu pour X questions") plutôt que de forcer une génération de mauvaise qualité.
- **Équipe** : 4 personnes.
- **Stack pressentie** : Python, Gradio (UI), FastAPI (API REST interne), Ollama (LLM), SQLite/PostgreSQL (profils + historique), Docker/Docker Compose, pytest (tests unitaires).

## 1. Répartition des rôles (équipe de 4)

| Rôle | Responsabilités principales |
|---|---|
| **Dev A — Backend & Orchestration LLM** | API REST, intégration Ollama, prompt engineering génération, gestion du pipeline (ingestion → génération → validation → export) |
| **Dev B — Data & Qualité IA** | Parsing PDF/Markdown, extraction de concepts, prompts de contrôle qualité (anti-répétition, anti-verbatim, criticité), logique disciplinaire (maths vs cours théorique) |
| **Dev C — Frontend & UX** | Interface Gradio, maquettes (basse puis haute fidélité), écran profil/historique, ergonomie du feedback utilisateur |

## 3. Backlog détaillé (User Stories)

Format : `US-xx | En tant que... je veux... afin de...` + critères d'acceptation (CA) + estimation en points (Fibonacci) + rôle porteur.

### E1 — Cadrage & gouvernance

- **US-01** (3 pts, Dev PM/A) — En tant qu'équipe, je veux un **cahier des charges** validé afin de cadrer le périmètre.
  CA : document listant objectifs, contraintes (Ollama local, gemma4:12b), fonctionnalités MoSCoW, planning macro, critères de succès. Validé par les 4 membres.
- **US-02** (2 pts, Dev C) — En tant qu'équipe, je veux des **maquettes basse-fidélité** (wireframes) de l'interface afin d'aligner la vision UX avant le code.
  CA : au moins 3 écrans (upload, génération/édition QCM, historique/profil) en wireframe (Figma/papier/Excalidraw).
- **US-03** (2 pts, Dev D) — En tant que dev, je veux un **dépôt Git structuré** (mono-repo, conventions de commit, CI de base) afin de démarrer proprement.
  CA : repo avec arborescence `backend/`, `frontend/`, `docker/`, `tests/`, README, `.gitignore`, pipeline CI qui lance au moins un lint.
- **US-04** (1 pt, PM) — En tant que chef de projet, je veux un **backlog priorisé et sprinté** (ce présent document) afin de piloter l'avancement.

### E2 — Ingestion documentaire

- **US-05** (5 pts, Dev B) — En tant qu'enseignant, je veux **uploader un PDF** afin d'en extraire le texte brut.
  CA : extraction texte + structure (titres) via une lib type `pdfplumber`/`PyMuPDF` ; gestion des PDF scannés signalée comme non supportée (message clair, pas de plantage).
- **US-06** (3 pts, Dev B) — En tant qu'enseignant, je veux **uploader un fichier Markdown** afin d'en extraire le contenu structuré.
  CA : parsing des titres/sections Markdown conservé pour segmenter le cours par notion.
- **US-07** (3 pts, Dev B) — En tant que système, je veux **segmenter le texte extrait par notion/section** afin de générer des QCM ciblés plutôt qu'un bloc unique.
  CA : découpage basé sur les titres ; chaque section obtient un identifiant + un résumé de longueur.
- **US-08** (2 pts, Dev B) — En tant que système, je veux **détecter la discipline/nature du contenu** (cours théorique vs. maths/exercices) afin d'adapter la stratégie de génération.
  CA : heuristique simple (mots-clés, présence de formules/LaTeX, densité de symboles) + champ `type_contenu` stocké.

### E3 — Génération contrainte de QCM

- **US-09** (5 pts, Dev A) — En tant que backend, je veux un **client d'appel REST vers Ollama** afin d'interroger `gemma4:12b` de façon fiabilisée (timeout, retry, gestion d'erreurs).
  CA : module réutilisable, testé avec un mock d'Ollama, logs des appels.
- **US-10** (5 pts, Dev A) — En tant qu'enseignant, je veux que le système **extraie les concepts clés** d'une section afin de savoir sur quoi générer des questions.
  CA : prompt dédié retournant une liste de concepts avec leur section source.
- **US-11** (8 pts, Dev A) — En tant qu'enseignant, je veux **générer un QCM au format JSON strict** (question, bonne réponse, 3 distracteurs, explication) afin de l'exploiter automatiquement.
  CA : schéma JSON validé (ex. via `pydantic`/`jsonschema`) ; en cas de sortie invalide, une tentative de re-génération automatique est faite ; échec géré proprement (message à l'utilisateur, pas de crash).
- **US-12** (3 pts, Dev A) — En tant qu'enseignant, je veux **choisir le nombre de questions** à générer afin d'adapter la charge du QCM.
  CA : paramètre exposé dans l'API et l'UI, valeur par défaut = dernière valeur utilisée par l'utilisateur (lien avec US-24).

### E4 — Anti-verbatim & créativité disciplinaire

- **US-13** (5 pts, Dev B) — En tant qu'enseignant, je veux que les **questions ne reprennent jamais des phrases du cours telles quelles** afin d'évaluer la compréhension et non le par-cœur.
  CA : prompt imposant une reformulation/mise en situation ; test automatique de similarité texte (ex. ratio de n-grammes communs) entre question générée et texte source, avec seuil de rejet + régénération si dépassé.
- **US-14** (5 pts, Dev B) — En tant qu'enseignant de maths, je veux que le système **génère des exercices d'application** (calcul, résolution) à partir du cours plutôt que des questions de restitution afin de tester la compétence réelle.
  CA : prompt spécifique déclenché quand `type_contenu = maths/exercice` (cf. US-08), avec exemples few-shot ; vérification qu'au moins une opération/calcul apparaît dans la question générée.
- **US-15** (3 pts, Dev B) — En tant qu'enseignant, je veux pouvoir **choisir un mode de génération** (restitution de connaissance vs. application/exercice) afin de garder la main sur la pédagogie.
  CA : sélecteur exposé en UI, transmis au prompt.

### E5 — Contrôle qualité des distracteurs

- **US-16** (5 pts, Dev B) — En tant que système, je veux **faire relire chaque QCM par le LLM en tant que "correcteur"** afin de détecter les distracteurs ambigus ou involontairement corrects.
  CA : second appel LLM avec prompt de validation, retour structuré (`valide: bool`, `raison`) par distracteur.
- **US-17** (3 pts, Dev A) — En tant que système, je veux **régénérer automatiquement** un distracteur rejeté par le contrôle qualité afin de ne pas bloquer tout le QCM.
  CA : boucle de correction limitée (ex. 2 tentatives max), sinon la question est marquée "à revoir manuellement".
- **US-18** (2 pts, Dev C) — En tant qu'enseignant, je veux **voir visuellement quelles questions ont été signalées** par le contrôle qualité afin de les relire en priorité.
  CA : badge/couleur dans l'UI sur les questions marquées "à revoir".

### E6 — Anti-répétition entre générations

- **US-19** (5 pts, Dev A) — En tant qu'enseignant, je veux que **relancer une génération sur le même support ne donne jamais le même QCM** afin de varier les évaluations (ex. plusieurs classes, plusieurs tentatives).
  CA : stockage d'un hash/empreinte des questions déjà générées pour ce support+utilisateur ; le prompt inclut une consigne explicite de variation + une liste des angles déjà couverts ; test vérifiant que 2 générations successives ont un taux de similarité de questions sous un seuil défini.
- **US-20** (2 pts, Dev D) — En tant que système, je veux **stocker l'historique des QCM générés par support** afin d'alimenter la logique anti-répétition et l'historique utilisateur.
  CA : table `generations` liée à `documents` et `users`.

### E7 — Profils utilisateurs & historique

- **US-21** (5 pts, Dev D) — En tant qu'enseignant, je veux **avoir un compte/profil** afin de retrouver mes documents et mes QCM précédents.
  CA : authentification simple (login/mot de passe ou SSO IUT si dispo) ; conteneurisé, données persistées dans un volume Docker.
- **US-22** (3 pts, Dev D) — En tant qu'enseignant, je veux **consulter l'historique de mes générations** afin de réutiliser ou comparer d'anciens QCM.
  CA : écran listant support, date, nombre de questions, statut (validé, à revoir, supprimé).
- **US-23** (3 pts, Dev D) — En tant que système, je veux que **toutes les données (profils, documents, QCM) soient persistées via Docker volumes/DB** afin de respecter la contrainte de souveraineté et de survie aux redémarrages.
  CA : `docker-compose.yml` avec service DB + volume nommé ; test de redémarrage sans perte de données.

### E8 — Feedback utilisateur & apprentissage des préférences

- **US-24** (5 pts, Dev A) — En tant que système, je veux **mémoriser les préférences explicites** (ex. nombre de questions demandé) afin de les réappliquer par défaut aux prochaines générations du même utilisateur.
  CA : table `preferences_utilisateur` ; les valeurs par défaut des formulaires de génération sont pré-remplies avec la dernière préférence connue.
- **US-25** (5 pts, Dev B) — En tant qu'enseignant, je veux pouvoir **rejeter en bloc un QCM en donnant une raison** (ex. "mal fait") afin que le système en tienne compte pour la suite.
  CA : bouton "Rejeter tout" + champ de commentaire libre ; l'information est stockée et injectée (résumée) dans les prompts futurs pour ce support/utilisateur (ex. "l'utilisateur a rejeté une génération précédente pour raison X, éviter de reproduire ce défaut").
- **US-26** (3 pts, Dev C) — En tant qu'enseignant, je veux **noter/valider chaque question individuellement** (👍/👎) afin d'affiner progressivement la qualité perçue.
  CA : UI de notation par question, stockage en base, agrégation visible dans l'historique.

### E9 — Posture critique de l'IA

- **US-27** (5 pts, Dev B) — En tant qu'enseignant, je veux que le système **refuse ou m'alerte si le support est trop court/pauvre** pour générer le nombre de questions demandé afin d'éviter des QCM artificiels ou redondants.
  CA : heuristique (longueur du texte, nombre de concepts extraits) comparée au nombre de questions demandé ; si ratio insuffisant, message explicite ("Contenu insuffisant pour générer 10 questions distinctes, 4 questions de qualité peuvent être proposées à la place") + proposition d'un nombre alternatif.
- **US-28** (3 pts, Dev A) — En tant qu'enseignant, je veux que **l'IA justifie ses refus/alertes** afin de comprendre et éventuellement enrichir mon support.
  CA : message d'alerte accompagné d'une explication concrète (ex. "seulement 2 concepts distincts identifiés").

### E10 — Export standardisé

- **US-29** (5 pts, Dev D) — En tant qu'enseignant, je veux **exporter un QCM au format GIFT** afin de l'importer dans Moodle.
  CA : génération d'un fichier `.txt` conforme à la syntaxe GIFT, incluant feedback ; test d'import réel dans une instance Moodle de test si disponible.
- **US-30** (5 pts, Dev D) — En tant qu'enseignant, je veux **exporter un QCM au format XML Moodle** afin de disposer d'une alternative interopérable.
  CA : fichier XML conforme au schéma Moodle QTI/Moodle XML, avec bonne réponse marquée et feedback par réponse.
- **US-31** (2 pts, Dev C) — En tant qu'enseignant, je veux **télécharger l'export directement depuis l'interface** afin de ne pas manipuler de fichiers serveur.
  CA : bouton de téléchargement dans Gradio, nom de fichier explicite (support + date).

### E11 — Interface Gradio & maquettes

- **US-32** (5 pts, Dev C) — En tant qu'enseignant, je veux une **interface Gradio d'upload et de configuration** (nombre de questions, mode restitution/exercice) afin de lancer une génération simplement.
  CA : formulaire fonctionnel connecté à l'API backend.
- **US-33** (5 pts, Dev C) — En tant qu'enseignant, je veux une **interface d'édition/validation des QCM générés** afin de corriger avant export.
  CA : édition inline de la question, des distracteurs et du feedback ; sauvegarde des modifications.
- **US-34** (3 pts, Dev C) — En tant qu'enseignant, je veux une **interface de profil/historique** afin de gérer mes documents et préférences.
  CA : écran listant historique + préférences actuelles + possibilité de les modifier manuellement.
- **US-35** (3 pts, Dev C) — En tant qu'équipe, je veux des **maquettes haute-fidélité** validées afin de guider le développement final de l'UI.
  CA : maquettes couvrant les 4 écrans clés, validées par l'équipe avant développement du Sprint concerné.

### E12 — Infrastructure, tests, qualité logicielle

- **US-36** (5 pts, Dev D) — En tant qu'équipe, je veux un **environnement Docker Compose complet** (backend, frontend, DB, Ollama) afin de garantir la reproductibilité sur tous les postes.
  CA : `docker-compose up` lance l'ensemble de la stack en une commande, documenté dans le README.
- **US-37** (5 pts, Dev D, transverse) — En tant qu'équipe, je veux des **tests unitaires** sur les modules critiques (parsing, génération JSON, contrôle qualité, export) afin de sécuriser les évolutions.
  CA : couverture minimale définie (ex. 60%) sur les modules backend, exécutés en CI.
- **US-38** (2 pts, Dev D) — En tant qu'équipe, je veux une **CI qui exécute lint + tests à chaque push** afin de détecter les régressions tôt.

## 4. Planning en sprints

Découpage proposé sur **10 semaines**, sprints de 2 semaines (sauf Sprint 0 = cadrage sur 1 semaine, conforme à ta contrainte "CA fait en semaine 1").

### Sprint 0 — Semaine 1 : Cadrage
Objectif : livrer le cahier des charges et poser les bases techniques.
- US-01, US-02, US-03, US-04
- Livrable clé : **Cahier des charges validé** + wireframes + repo initialisé.

### Sprint 1 — Semaines 2-3 : Fondations techniques
Objectif : la donnée circule de bout en bout (upload → texte extrait), l'infra tourne.
- US-05, US-06, US-07, US-08 (ingestion)
- US-09 (client Ollama)
- US-36 (Docker Compose complet)
- US-32 (UI upload minimal)
- Démo de sprint : upload d'un PDF/Markdown → texte segmenté visible, Ollama joignable via l'app.

### Sprint 2 — Semaines 4-5 : Génération QCM de base
Objectif : premier bout-en-bout génération JSON, avec persistance et profils.
- US-10, US-11, US-12 (génération)
- US-21, US-22, US-23 (profils/historique/Docker persistant)
- US-33 (UI édition/validation basique)
- Démo de sprint : un enseignant se connecte, upload un support, obtient un QCM JSON affiché et éditable.

### Sprint 3 — Semaines 6-7 : Qualité pédagogique
Objectif : QCM réellement fiables et non redondants.
- US-13, US-14, US-15 (anti-verbatim / maths)
- US-16, US-17, US-18 (contrôle qualité distracteurs)
- US-19, US-20 (anti-répétition)
- US-27, US-28 (posture critique)
- Démo de sprint : régénérer deux fois le même support donne deux QCM différents ; un support trop pauvre déclenche une alerte.

### Sprint 4 — Semaines 8-9 : Personnalisation & export
Objectif : le produit apprend de l'utilisateur et devient exploitable en LMS.
- US-24, US-25, US-26 (préférences & feedback)
- US-29, US-30, US-31 (export GIFT/Moodle XML)
- US-34, US-35 (UI profil + maquettes finales alignées)
- Démo de sprint : préférence "5 questions" réappliquée automatiquement ; export GIFT importé dans Moodle de test.

### Sprint 5 — Semaine 10 : Stabilisation & recette
Objectif : qualité logicielle et présentation finale.
- US-37, US-38 (tests unitaires + CI, finalisés/complétés)
- Corrections issues des démos précédentes
- Recette globale, préparation de la soutenance/démo finale

## 5. Contenu attendu du Cahier des charges (Semaine 1)

Pour tenir le délai d'une semaine, structure-le simplement :
1. Contexte et enjeux pédagogiques
2. Objectifs et périmètre (MoSCoW : Must/Should/Could/Won't)
3. Contraintes techniques (100% local, Ollama, `gemma4:12b`, Docker)
4. Utilisateurs cibles et parcours principal
5. Exigences non-fonctionnelles (souveraineté des données, reproductibilité, coûts)
6. Planning macro (les sprints ci-dessus)
7. Répartition des rôles
8. Risques identifiés (ex. qualité des distracteurs générés, temps de génération avec un modèle 12B en local, taille des supports vs. capacité contextuelle)

## 6. Points de vigilance transverses (à rappeler à chaque sprint review)

- **Non-répétition** (US-19) et **anti-verbatim** (US-13/14) sont les fonctionnalités les plus à risque techniquement : prévoir du temps de test avec de vrais supports de cours dès le Sprint 3, pas seulement en fin de projet.
- Le **contrôle qualité** (US-16/17) double le nombre d'appels LLM par QCM : surveiller les temps de réponse d'un modèle 12B en local et prévoir un indicateur de progression dans l'UI.
- **Docker + profils** (E7) doit être posé tôt (Sprint 2) car l'historique et les préférences (E8) en dépendent directement.
